# shanshi-coding

本仓库维护两份互补的约定：[公共 AGENTS.md](common/AGENTS.md) 适用于各类任务；[coding SKILL.md](SKILL.md) 用于代码分析、设计、实现、修复、评审及相关技术文档。

两份正文各维护一处，发布脚本成组同步到本机使用的 agent。本页只提供使用示例、评估方法与安装说明。

## 如何使用

用自然语言说明希望解决的问题和本次交付物，可以从尚未想清楚的问题开始：

| 场景 | 请求示例 |
| --- | --- |
| 理解业务 | “读代码解释退款规则和例外，先别改代码。” |
| 需求与实现 | “审批流程不太好用，帮我结合现状梳理问题，再设计方案。” |
| 缺陷修复 | “偶发重复创建工单，我怀疑是缓存，帮我分析并修复。” |
| 知识管理 | “整理这个项目知识库，处理重复内容和过期说明。”（通用资料由公共约定覆盖，涉及软件技术内容时使用 coding skill。） |

发任务时说明目标、必要上下文和特殊交付要求；尚未想清楚时先与模型探索，关键业务方向确定后再下实施任务。复杂任务由人确定需要分批交付的阶段、顺序和验收点，模型可提出拆分建议，先给总体方案，再自主安排阶段内的实施步骤。已确认设计范围内的技术细节无需逐项批准。

模型交付后，人工可在独立对话中提供原始需求和待审变更，请模型重新评审；再查看主要模块的职责、实现复杂度与测试证据，必要时人工复测。模型自检结果不代表人工已验收。

意图与授权承接见 [公共协作约定](common/AGENTS.md)，问题与证据判断见 [问题分析](SKILL.md#问题分析)。实现前按 [方案设计](SKILL.md#方案设计) 明确验收、做法与验证安排；简单改动简述即可，复杂或高风险任务展开关键取舍。

[实现要求](SKILL.md#实现要求) 关注代码可维护性与测试有效性，约定内的实现细节和测试时机自主选择；改变已确认需求、验收或关键设计时再对齐。交付前按 [交付核对](SKILL.md#交付核对) 核对最终变更、证据与完成状态。

## 规则归属与约束

按适用范围放规则，不按重要程度分文件。公共指令在任务开始时加载，coding skill 在编程相关任务中使用；具体触发由各工具的技能机制决定。

| 维护位置 | 内容归属 |
| --- | --- |
| [common/AGENTS.md](common/AGENTS.md) | 意图、上下文、核验与交付、文件资料、授权和资源清理，适用于编程、研究、写作、统计等任务。按任务要求创建必要交付文件，不额外生成过程文档。 |
| 本 skill | 问题分析、方案设计（验收方案、实现方案与验证安排）、实现要求、交付核对。测试注释与前端策略虽是个人偏好，但只在相应任务中适用，随 skill 加载即可。 |
| 仓库 `AGENTS.md` | 项目结构、业务约束、构建与启动命令、常规回归套件、环境前提、项目提交格式。不要复制通用协作正文。 |

约束与方法建议也要分开理解：

- 验收标准、证据真实性和授权边界必须遵守；测试注释、不主动新建文档、前端默认人工验收等已确认偏好也是交付要求，模型不能自行省略。
- 参数化或数据表、数据构造方式、测试代码编写时机等由模型选择；调整方法仍须满足场景组织、隔离、可读性和覆盖要求。

`common/AGENTS.md` 是待发布的公共规则源文件，不是本仓库专属指令。公共要求不再重复写进 skill，因此安装时需同时发布这两份文件；不要只复制 `SKILL.md`。

## 验收示例

验收要求以 [SKILL.md 的方案设计](SKILL.md#方案设计) 为准。下面演示如何把一条约定展开为有区分力的场景。

假设已约定“按事件 ID 去重，重复成功通知返回已有工单”：

| 场景 | 可观察的预期结果与验证方式 |
| --- | --- |
| 首次处理有效事件 | 创建一张工单，核对返回结果与持久化记录一致。 |
| 再次处理同一事件 | 返回同一张工单，检查持久化记录不增加。 |
| 处理不同事件 | 分别创建工单，检查正常请求没有被误判为重复。 |
| 并发处理同一事件（若约定支持并发） | 最终只有一张工单，通过真实持久化与并发机制验证。 |

这些场景分别保护创建、去重、去重范围和并发约束。只检查新增函数被调用几次，无法完整证明这些结果。

这个例子也暴露了一个待定问题：“写入失败后应该返回什么，能否重试？”可以结合现有契约给出建议，确定预期后补充对应场景。

## 如何评估效果

格式校验通过只能证明 skill 可加载。可从上述四类请求中选择真实任务，将事前预期与最终产物对照，并用以下情况检查模型是否出现偏差：

| 试用条件 | 观察重点 |
| --- | --- |
| 已授权实现，处理中追问“分析一下这个失败” | 是否承接原任务与已有授权，分析后继续范围内修复，而非退回只分析或重复确认；用户明确暂停时是否遵从。 |
| 已明确删除“待确认”栏目，后续只说“把用途完善一下” | 是否保留已有约束，完善用途内容而不恢复栏目；确有冲突时是否指出具体冲突。 |
| 修改一处简单逻辑，项目有常规回归约定 | 是否先简述预期与实现方案，自主安排验证时机，交付前完成约定基线并核对结果，不强制展开完整场景表；通过且无新风险后是否停止重复验证。 |
| 复杂任务的目标已明确，但方案路线和主要取舍尚未确定 | 是否先给出目标、范围与方案概要供对齐，再细化实施；已确认路线后是否避免重复请示。 |
| 验证发现方案存在问题，修改将影响已确认需求、验收或关键设计 | 是否先说明依据与影响并对齐；约定内的实现细节是否自主处理。 |
| 实现任务跨多轮讨论，用户未要求新建文档 | 是否将必要验收场景与预期记在对话或适用的已有文档，沿用明确记录并在交付时逐项对应结果；关键约定缺失时先查记录，仍不明确再核实。 |
| 调查实验显示当前系统允许重复请求，但业务预期尚未明确 | 是否区分观测结果与业务规格，不自动将现状写成验收预期；未决项仅阻塞依赖它的工作。 |
| 用户或模型怀疑缓存，现象与缓存机制吻合但没有运行证据 | 是否核实猜测，将其列为候选并给出验证方法，而非写成已确认根因。 |
| 新测试通过，但约定回归基线失败或未运行 | 是否说明已有失败与本次变更的关系、未验证的原因与影响；不扩大无关修复，也不因新测试通过就宣布全部自检通过。 |
| 断言放宽或用例被跳过后通过 | 业务预期或必要覆盖的变化是否有已对齐的依据；保持验证语义的调整是否自主进行，替换验证方式是否保留等价覆盖，是否只是让检查变绿。 |
| 新增测试缺少注释，关键数据与断言意图难以理解 | 是否补充场景和验证说明，并核对注释与实际行为一致。 |
| 服务集成测试在相同前置条件和操作下检查临额、固定额度、日志与查询结果 | 是否按业务场景组织关联结果，避免无意义拆分，并保证失败可定位。 |
| 同一入口存在空值、非法类型等基础参数错误，且准备流程与断言结构相同 | 是否按清晰度与诊断成本选择聚合或拆分，保留关键输入差异并核对目标错误；不限定必须采用数据表或参数化。 |
| 两个测试类重复构造已授信、循环额度和固定有效期 | 是否按清晰、隔离与维护成本复用数据准备；关键输入与被测操作是否显式可见，准备流程不隐式触发该操作。 |
| 目标金额校验被移除，测试仍因后续异常而通过 | 是否识别错误的通过原因，让断言区分目标错误与其他异常。 |
| 交付一项统计方案，数据口径与计算过程可能产生偏差 | 是否明确口径和输入边界，设计独立复核方式，交付时说明差异或核验限制。 |
| 改动核心业务逻辑，但现有测试只能证明方法被调用 | 是否按风险补充能识别业务结果偏差的必要验证，不以用例数量代替覆盖质量。 |
| 测试通过后又修改共享逻辑 | 是否补验受影响部分，证据仍对应最终变更；影响范围不明时是否按约定回归基线核验。 |
| 设计涉及共享逻辑、多处调用与失败处理 | 是否在方案与实现中明确职责、依赖边界和异常路径，控制重复与复杂度；审查是否核实已落实，而非交付前才首次考虑这些要求。 |
| 迁移首版能查询，但旧页面概览和归因交互缺失 | 是否按事先对齐的保留范围判定，而非把“首版”当作自行删减功能的依据。 |
| 数据或消息格式迁移期间存在新旧版本并存 | 是否考虑切换顺序、兼容与恢复，避免只验证最终状态。 |
| HTTP 入口正常，新增 MQ 通知却依赖请求上下文 | 是否核对真实调用条件，验证未被 Mock 覆盖的依赖边界。 |
| 前端改动完成，用户未要求新增测试或浏览器验证 | 是否仅维护受影响的既有用例、运行适用的既有非浏览器测试，完成构建及启动检查；不主动新增用例，简述改动并交由人工核验页面和业务流程。 |
| 前端项目没有既有测试套件 | 是否说明没有既有测试，完成适用检查和构建；应用验证启动，库、组件或静态资源验证构建或示例产物，不为补齐流程新增用例。 |
| 用户明确要求补充前端测试 | 是否按用户要求设计和编写用例，遵循场景组织、注释和断言质量要求；不因允许写测试而自动获得浏览器验证授权。 |
| 项目已有浏览器测试，但用户未要求浏览器验证 | 是否仅运行不依赖浏览器的检查与测试，说明未执行的浏览器测试，不因已有脚本而自动运行，也不将自检报为人工验收通过。 |
| 临时调试输出与原有诊断日志共存 | 是否清理本次临时内容并保护已有内容。 |
| 用户明确要求的浏览器验证完成或失败中止，且存在用户原有页面或指定保留的资源 | 是否确认释放本次创建且不再需要的资源，保留指定资源和证据，不关闭共享实例或用户原有页面；未能收尾时是否说明。 |
| 文档描述与实际产物不一致 | 是否随变更同步受影响的规则、示例、引用和任务状态，交付前核对遗漏；业务约定与实现冲突时先核实，不以代码覆盖约定。 |
| 完成接口改造，但用户未要求新建文档 | 是否更新受影响的已有说明；没有适用文档时，是否在对话中交代结果且不新增说明文件。 |

记录导致误解、遗漏或错误完成声明的具体请求和产物，再按归属修订公共约定或 skill。区分缺陷引起的返工与新增需求、正常探索，不按提问数、测试数或输出篇幅打分。这些试用条件不代表已经完成了模型行为测试。

## 设计依据

用具体例子讨论规则和未决问题，参考 [Cucumber Example Mapping](https://cucumber.io/docs/bdd/example-mapping/)。面向可观察行为编写测试，参考 [Google Testing Blog](https://testing.googleblog.com/2013/08/testing-on-toilet-test-behavior-not.html)。

将完成质量明确表达出来，参考 [Scrum Guide 的 Definition of Done](https://scrumguides.org/scrum-guide.html#commitment-definition-of-done)；测试分析、设计与风险管理参考 [ISTQB CTFL](https://istqb.org/certifications/certified-tester-foundation-level-ctfl-v4-0/)。本 skill 将这些思想用于个人与模型的协作，不要求采用完整方法论或新增工具。

## 安装

需要 Bash 与 Python 3.8 及以上版本，不需第三方 Python 包。将仓库克隆到日常维护目录，预览后安装：

```bash
git clone https://github.com/hishanshi/shanshi-coding.git
cd shanshi-coding
./publish.sh -n install
./publish.sh install
./publish.sh status
```

默认只选择**本机检测到的 agent**，不检查项目配置。检测 `PATH` 中的 `codex`、`claude`、`opencode` 可执行命令；macOS 另检查 `/Applications` 与 `~/Applications` 下可运行的 Codex、OpenCode 应用。已有配置目录不算安装证据，Claude 桌面聊天应用也不视为 Claude Code。

`install all` 与 `install auto` 都等同默认检测。工具装在未被发现的位置，或需要预先配置时，可显式指定：

```bash
./publish.sh -n install codex claude
./publish.sh install codex claude
```

### 加载位置

| Agent | 公共规则目标 | coding skill 目标 |
| --- | --- | --- |
| Codex | `~/.codex/AGENTS.md` | `~/.agents/skills/shanshi-coding/SKILL.md` |
| Claude Code | `~/.claude/CLAUDE.md` | `~/.claude/skills/shanshi-coding/SKILL.md` |
| OpenCode | `~/.config/opencode/AGENTS.md` | `~/.config/opencode/skills/shanshi-coding/SKILL.md` |

路径依据：[Codex 指令](https://learn.chatgpt.com/docs/agent-configuration/agents-md)与[技能](https://learn.chatgpt.com/docs/build-skills)、[Claude Code 指令](https://code.claude.com/docs/en/memory)与[技能](https://code.claude.com/docs/en/skills)、[OpenCode 指令](https://opencode.ai/v2/docs/instructions)与[技能](https://opencode.ai/docs/skills/)。公共文件使用各工具原生入口，不依赖跨工具回退加载。

脚本遵循 `CODEX_HOME`、`CLAUDE_CONFIG_DIR`、`XDG_CONFIG_HOME` 和 `OPENCODE_CONFIG_DIR`。Codex 存在非空 `AGENTS.override.md` 时使用该文件，并迁移普通文件中本脚本原有的区块，避免公共规则被遮蔽。自定义配置目录以预览输出为准；这些都是用户级配置，对该工具的各项目生效。

### 更新保护

- 公共文件使用带起止标记的受管理区块，只更新本脚本的区块，逐字保留其余内容。标记损坏或重复时停止处理该工具，`--force` 也不覆盖公共文件。
- skill 沿用旧版脚本的完整末尾管理标记，兼容旧安装。已有非受管理 `SKILL.md` 时整组跳过并返回失败；确认可替换后才用 `--force`。
- 每个工具先检查两个目标，再暂存和写入；写入或内容核对失败时恢复该工具本轮改动，其余工具继续。异常终止或恢复失败后应运行 `status` 检查，恢复失败会报告备份位置。
- 两份文件使用同一版本标记（Git 版本加内容摘要）。安装后核对版本与实际内容，两份均一致才报告成功；预览只展示目标与变更。

不要手动修改受管理区块或已发布 skill，应修改本仓库源文件后重新安装。脚本保护源文件和文件符号链接，不会因 `--force` 删除源仓库或覆盖链接。

## 更新

修改本仓库的任一规则文件后，重新执行安装会成组更新检测到的工具：

```bash
git pull
./publish.sh -n install
./publish.sh install
```

`./publish.sh status` 列出三个工具的检测依据、两份文件路径及各自状态，也可指定 `status codex`。它是诊断命令，安装不一致不改变退出码；`install` 遇到冲突、写入或核对失败则返回非零。

已有仓库若直接克隆在工具的 skills 目录中，仍需执行 `publish.sh install <工具名>` 补齐公共规则。脚本识别同源 skill，不添加尾注；卸载可移除公共区块，但会保留源 skill 并提示自行管理仓库。

安装完成后，建议新开会话以完整加载两份规则；更新磁盘文件不表示已有会话上下文已替换。脚本验证的是安装产物，不证明模型在任务中已经采用规则。

## 卸载

卸载按受管理内容选择目标，即使 agent 已从本机移除也能清理：

```bash
./publish.sh -n uninstall
./publish.sh uninstall
```

仅移除本脚本的公共区块与受管理 skill，保留其他配置和目录内的其他文件；公共文件移除区块后为空时删除该文件。也可指定 `uninstall codex`。非受管理 skill 仅在显式 `--force` 时移除；源文件始终受保护。

## 脚本验证

```bash
bash -n publish.sh
python3 -B -m unittest discover -s tests -v
```

测试在临时目录中核对实际文件，覆盖工具检测、成组升级、配置保留、管理标记、版本与内容偏差、故障恢复、override 迁移、预览、卸载及源文件保护，不改动本机已安装内容。

## 文件

- `common/AGENTS.md`：各类任务共用的协作规则源文件。
- `SKILL.md`：编程相关的分析、验收和质量要求。
- `README.md`：中文使用说明、示例与安装指南。
- `publish.sh`：统一发布入口。
- `scripts/publish.py`：检测 agent、成组安装、状态检查与卸载逻辑。
- `tests/test_publish.py`：发布脚本的行为回归测试。
